## הבעיה

היום כל תיוק עובר דרך Claude: חלון תיבת הייצוא פונה ל-Claude אוטומטית בכל שינוי בבחירה, ובתוסף ה-Outlook
התיוק הוא שיחה עם Claude. השרת מבצע רק תוכנית ש-Claude הציע (`b.plan`), כך שבלי Claude אי אפשר לתייק בכלל.
ב-10 משתמשים זה מאות פניות ביום על חשבון מפתח ה-API של המשרד, בעוד שרוב התעבורה — פרסום ל-SENT/UPDATED
וקבלת תכניות מיועץ — היא כללים קבועים שקוד יכול לבצע.

**המטרה:** מודל היברידי. הקוד בונה את התוכנית מהמפה השמורה של הפרויקט, מעץ התיקיות האמיתי ומבחירות
המשתמש, בלי API. Claude נשאר זמין בכפתור "הצע" למקרים חריגים, ולמיפוי הראשוני של פרויקט שהשמות בו עקומים.

## 1. המפה: מה נשמר לכל פרויקט

היום ב-`filing.json` לכל פרויקט: `folder`, `root`, `guide`, `map: { areas: { <7 תחומים>: { paths[], note } } }`.
נוסף ל-`map` אובייקט `slots`:

```js
slots: {
  sent: 'PUBLISH/4021-pub-@sent',                          // ארכיון SENT ('' = לא מופה)
  sentSplit: true,                                         // true = תת-תיקייה לפי סוג קובץ, false = מאוחד
  updated: 'PUBLISH/4021-pub-updated/4021-pub-updated-PDF' // UPDATED של PUBLISH, PDF בלבד ('' = לא מופה)
}
```

- הנתיבים יחסיים לתיקיית הפרויקט ועוברים את `relPath` כמו נתיבי התחומים. נתיב שלא בעץ בזמן השמירה נדחה.
- `sentSplit` ברירת מחדל `true` (המוסכמה של היום).
- CONSULTANTS, RECEIVE, PERMIT ו-EXEC נשארים **תחומים** במפה (`areas.<key>.paths`), כמו היום. אין להם slot.
- `normalizeMap` מחזיר `slots` מנוקה (מפתחות ידועים בלבד). מפה ישנה בלי `slots` נקראת כ-slots ריקים.

**מה לא נשמר ונקרא מהעץ בכל תיוק** (העוזר כבר קורא את העץ, בלי API): רשימת היועצים (תת-התיקיות של
תחום CONSULTANTS, כמו `receiveOptions` היום), תיקיית התכניות והגרסאות של כל יועץ, ותת-התיקיות של
RECEIVE / PERMIT / EXEC. יועץ חדש מופיע ברגע שיש לו תיקייה.

### מילוי אוטומטי

פונקציה טהורה `autoSlots(tree, code)` ב-`filing-plan.js` (בלי Claude, ראו "שרת"), שמחזירה הצעה ל-`slots` ולתחומים:

- `sent`: התיקייה הראשונה בעץ ששמה מסתיים ב-`-pub-@sent` (לא תלוי רישיות).
- `updated`: תיקייה ששמה מסתיים ב-`-pub-updated-PDF`.
- תחומים: תיקייה בראש העץ או ברמה השנייה בשם `PUBLISH`, `CONSULTANTS`, `RECIEVE`/`RECEIVE`, `PERMIT`, `EXEC`
  (לא תלוי רישיות), כשהתחום עוד ריק.
- `sentSplit`: `true` אם מתחת ל-`sent` יש תיקיות תאריך שבתוכן `PDF`/`DWG`/`RVT`/`DOCS`; `false` אם יש תיקיות
  תאריך בלי תת-תיקיות כאלה; ברירת מחדל `true` כשאין עדיין תאריכים.

מה שלא נמצא נשאר ריק. ההצעה לא נשמרת לבד: המשתמש רואה אותה ושומר.

### בהגדרות הפרויקט ← תיקיות הפרויקט (`SettingsFoldersView`)

נוסף מקטע **"תיוק בלי Claude"** מתחת לבחירת התיקייה הראשית:

```
ארכיון SENT:     PUBLISH/4021-pub-@sent                       [בחר מהעץ]
  ◉ לפי סוג קובץ (PDF / DWG / RVT / DOCS)   ○ מאוחד
UPDATED (PDF):   PUBLISH/4021-pub-updated/4021-pub-updated-PDF [בחר מהעץ]
CONSULTANTS: CONSULTANTS   RECEIVE: RECIEVE   PERMIT: PERMIT   EXEC: EXEC   [בחר מהעץ]
[מלא אוטומטית]   [שמור]                    (מפה עם Claude — לפרויקטים שהשמות בהם לא לפי המוסכמה)
```

- "מלא אוטומטית" רץ גם לבד בפעם הראשונה שנבחרת תיקייה ראשית, וממלא רק שדות ריקים.
- "בחר מהעץ" בוחר מתוך העץ שהעוזר קרא (רשימה עם חיפוש), לא בבורר של Windows.
- שמירה דרך נתיב השרת הקיים של המפה, עם הבדיקות הקיימות. עריכה רק למי שיש לו הרשאת כתיבה בפרויקט (`writer`).

## 2. פרסום מתיבת הייצוא (`InboxBatch`, מצב publish)

```
תיבת הייצוא — 3 קבצים                         פרויקט: 4021 מגרש 4021  [החלף]
☑ A-101.pdf  ☑ A-102.pdf  ☑ A-101.dwg
☑ SENT   תאריך: [2026-10-26]
☑ UPDATED (PDF בלבד) — A-101.dwg יישמר רק ב-SENT
תוכנית:
  • תיקייה חדשה: …/4021-pub-sent-2026/4021-pub-2026,10,26/PDF
  • A-101.pdf, A-102.pdf ← …/4021-pub-2026,10,26/PDF            [📂]
  • A-101.dwg ← …/4021-pub-2026,10,26/DWG
  • A-101.pdf, A-102.pdf ← …/4021-pub-updated-PDF (מחליף, הישן ל-@ver)   [📂]
[אשר ופרסם]  [ביטול]
▸ הצע עם Claude (לרוב לא צריך)  [הוראה: ______]  [הצע]
```

**הזרימה:** בכל שינוי (קבצים, פרויקט, SENT, תאריך, UPDATED) החלון קורא ל-`inbox-plan` (ראו "שרת"), והתוכנית
מתעדכנת מיד. "אשר ופרסם" נשאר `inbox-confirm` כמו היום.

**נתיב SENT** (`sentDest(slots, tree, code, date, ext)`):
- שכבת השנה: אם תחת `sent` יש תיקיות `<משהו>-sent-YYYY`, התאריך נכנס לתיקיית השנה (`<code>-pub-sent-YYYY`,
  נוצרת כשחסרה). אם תיקיות התאריך יושבות ישר תחת `sent`, בלי שכבת שנה.
- תיקיית התאריך: `<code>-pub-YYYY,MM,DD`. כשיש כבר תיקייה לאותו תאריך — משתמשים בה, בשמה הקיים.
- `sentSplit`: תת-תיקייה לפי סיומת — `PDF`, `DWG`, `RVT`, אחרת `DOCS`. מאוחד: ישר בתיקיית התאריך.
- קובץ בשם קיים מקבל " (2)" (התנהגות העוזר היום, `replace: false`).

**UPDATED:** רק קבצי `.pdf` (לא תלוי רישיות) מקבלים יעד ב-`slots.updated` עם `replace: true`. החלון מציג
כמה קבצים לא נכנסים ל-UPDATED ולמה.

**כשחסר מיפוי:** בלי `slots.sent` — תיבת SENT מושבתת, וליד: "אין ארכיון SENT במפה — מפה בהגדרות הפרויקט"
(קישור). אותו דבר ל-UPDATED. בלי תיקייה ראשית — ההודעה הקיימת (`needsFolder`).

**"הצע":** קורא ל-`inbox-propose` הקיים, עם ההוראה. התוכנית של Claude מחליפה את התוכנית של הקוד ומוצגת
עם המילים שלו, כמו היום. שינוי אחר כך בבחירה חוזר לתוכנית של הקוד. בלי לחיצה — אין פנייה. ההנחיה ל-Claude
מתעדכנת: SENT לפי `slots.sent` ו-`sentSplit`, UPDATED ל-PDF בלבד ב-`slots.updated`.

**"תיקייה אחרת"** (`pick-source`) עובד באותו אופן; הקבצים רק מועתקים, כמו היום.

## 3. קבלת קבצים (חלון תיבת הייצוא, מצב receive, ותוסף ה-Outlook)

אותו טופס בשני המקומות:

```
פרויקט: 4021 מגרש 4021 [החלף]
ממי: [▾ קונסטרוקציה — KONS (דני כהן, מהנדס)]      ← יועצים | רשות, קבלן ואחרים
  ◉ תכניות   ○ מסמכים
  גרסה חדשה: 4021-KONS-plans-v04
  ☑ העבר את הגרסה הקיימת (…-v03) ל-@ver
תוכנית: …                                         [📂]
[אשר ותייק]   ▸ הצע עם Claude (לרוב לא צריך)
```

**ממי:** רשימה אחת בשתי קבוצות, מ-`receiveOptions` הקיים: יועצים (תת-התיקיות של CONSULTANTS, עם השם
מה-register) ורשות / קבלן / אחרים (תת-התיקיות של PERMIT, EXEC, RECEIVE). **בתוסף**, היועץ נבחר מראש כשכתובת
השולח מופיעה באנשי הקשר של הפרויקט ומשויכת לתיקיית יועץ (`receiveOptions` כבר משייך איש קשר לתיקייה; ההתאמה
לכתובת בקוד, בלי Claude). אין התאמה — אין בחירה מראש.

**תכניות של יועץ** (`planDest(consultantFolder, tree, code)`):
1. איפה הגרסאות: בתת-תיקייה של היועץ ששמה מסתיים ב-`-plans`; אם אין בה גרסאות ויש גרסאות ישר בתיקיית
   היועץ — שם. גרסה = שם תיקייה שתואם `^(.*)-v(\d{1,4})$` (אותו `VERSION` של `sanitizeReceivePlan` והעוזר).
2. יש גרסאות: הגבוהה ביותר + 1, אותו stem, אותה אות v (רישיות), אותו מספר ספרות או יותר כשצריך
   (`-v009` ← `-v010`). השדה מוצג לקריאה בלבד.
3. אין גרסאות ואין תיקייה בשם אחר: `<code>-<C>-plans/<code>-<C>-plans-v01` לפי המוסכמה (C = שם היועץ
   כפי שתיקייתו כתובה בלי קוד הפרויקט); `-plans` נוצרת כשחסרה. השדה מוצג לקריאה בלבד.
4. **יש תיקיות ב-`-plans` אבל אף אחת לא בפורמט הגרסה** (למשל `גרסה 3`): שדה שם **לעריכה** עם ההצעה מסעיף 3;
   צ'ק בוקס ה-`@ver` מושבת עם "העברה ל-@ver רק לתיקיות בשם …-vNN". השם נבדק ב-`relPath` (תווים חוקיים,
   תיקייה אחת, לא קיימת).

**☐ העבר את הגרסה הקיימת ל-@ver:** מוצג תמיד (חוץ מסעיף 4, ואין גרסה קודמת — מוסתר). מסומן מראש כשיש
ליד הגרסאות תיקייה עם `@ver` בשם. מסומן ואין תיקייה כזו — נוצרת `<stem>-@ver` (למשל `4021-KONS-plans-@ver`).
התוכנית: `mkdir` לגרסה החדשה, `mkdir` ל-`@ver` כשצריך, `move` של הקודמת — בדיוק הצעדים ש-`sanitizeReceivePlan`
והעוזר כבר מקבלים.

**מסמכים של יועץ:** תת-התיקייה של היועץ ששמה מסתיים ב-`-docs`; אין — `<code>-<C>-docs` נוצרת. בלי גרסאות.

**רשות / קבלן / אחרים:** הקבצים נכנסים לתת-התיקייה שנבחרה, כמו שהיא. בלי `mkdir`. מאחר שזו רק העתקה,
אותה בחירה משמשת גם לקבצים שהמשרד **שולח** לרשות או לקבלן (בחלון תיבת הייצוא).

**בתוסף ה-Outlook:** כרטיס "תיוק בתיקיית הפרויקט" נפתח על הטופס הזה במקום השיחה. הקבצים המצורפים —
אותו מסלול כמו היום: ב-Outlook הקלאסי העוזר שומר מהמחשב, אחרת העלאה לשרת עם תקרת 50 MB ביום. "הצע"
פותח את השיחה הקיימת עם Claude (תיבת ההוראה, תיקונים, "הוסף להנחיה"). אחרי ביצוע: 📂 ליד כל יעד, ורשומה
במשימה המקושרת כמו היום.

## 4. שרת

פונקציות טהורות חדשות בקובץ משלהן, `tools/local-server/filing-plan.js` (כדי שאפשר יהיה לבדוק אותן לבד), ש-`filing.js` משתמש בהן:
`autoSlots`, `sentDest`, `inboxPlan({ slots, tree, code, files, sent, updated, date })`,
`receivePlan({ tree, code, from, doc, versionName, toVer, files })`. כל אחת מחזירה תוכנית באותו מבנה של היום
(`{ files: [{ n, name, dests: [{ path, replace }] }], steps, mode }`), והיא עוברת את `sanitizeInboxPlan` /
`sanitizeReceivePlan` הקיימים — בדיוק כמו תוכנית של Claude.

נתיבים חדשים:

| נתיב | מה עושה |
|---|---|
| `POST /api/filing-hub/inbox-plan` | כמו `inbox-propose` בלי Claude: קורא את העץ (`treeOf`), בונה בקוד, שומר `b.plan`, מחזיר `{ plan, options }`. `options` לקבלה: היועצים, האחרים, שם הגרסה הבאה, האם יש `@ver`, האם השם לעריכה. |
| `POST /api/outlook/filing-plan` | אותו דבר לתוסף, על תיוק פתוח (`fJob`), שומר את התוכנית כ"תוכנית אחרונה" כמו `filing-propose`. |
| `GET/POST …/project` (קיים) | מחזיר ושומר גם את `map.slots`. |
| `POST …/map-auto` | מחזיר `autoSlots` על העץ, בלי לשמור. |

`inbox-confirm` ו-`filing-confirm` לא משתנים: הם שולחים לעוזר את התוכנית ששמורה בשרת, לא מה שהדף שלח.
