# מסלול המכרז (Tender Track) — מסמך עיצוב

**תאריך:** 2026-09-06
**קובץ יעד:** `project_hub_01.html`
**רפרנס בסיס:** `planning_dashboard.html` (מטריצת מסמכים — consultants × docTypes × buildings)
**סטטוס:** אושר בברֵינסטורם, ממתין לתכנון יישום

---

## 1. מטרה

מסלול חדש ב-Project Hub לניהול **ספרינט המכרז**: לוודא שלכל יועץ יש את כל המסמכים
הנדרשים למכרז (תכניות, מפרט, כתב כמויות ועוד). התצוגה היא **דאשבורד-מטריצה** שנותן
למשתמש תמונת מצב מיידית — מה **חסר**, מה **בעבודה**, מה **תקוע**, ומה **הסתיים** —
לכל צירוף של מבנה × יועץ × סוג-מסמך.

זה שונה משאר המסלולים (רישוי/תכנון): לא רשימת משימות אלא מטריצת-כיסוי.

## 2. מטרות-על ולא-מטרות

**בתחום:**
- סוג גיליון חדש `tender` (מטריצה) שיושב במסלול העליון "מכרז".
- תצוגת דאשבורד: אריחי-סיכום + מטריצה pivot-בילית + מסננים.
- סטטוס תא נגזר מאירועים (כמו שאר Project Hub) + override ידני.
- תמיכה ב-N מבנים (אולם ספורט לוד = מבנה אחד, אבל המבנה נתמך לריבוי).

**לא בתחום (YAGNI):**
- אין ריבוי-פרויקטים / תבניות מסלול (עתידי).
- אין אוטומציות על תאי-מכרז בשלב זה.
- אין ייצוא/דוחות ייעודיים למכרז בשלב זה.

## 3. אינטגרציה וניווט

- מסלול עליון "מכרז" **כבר קיים** ב-`makeDefaultData().tracks`:
  `{id:"tender", label:"מסלול מכרז", trackValue:"tender", stageOrder:[]}`.
  אנחנו ממלאים scaffolding קיים, לא ממציאים ניווט.
- גיליונות משתייכים למסלול דרך השדה `sheet.track` (למשל `"licensing"`).
- **נוסיף גיליון אחד** מסוג `type:'tender'` עם `track:'tender'`.
- **מונח כפול-משמעות (זהירות):** ב-Project Hub "track" מופיע בשתי משמעויות שונות —
  (א) מסלול-ניווט עליון (`data.tracks`, `sheet.track`), ו-(ב) "track" ברמת-משימה
  (נתיב יועץ בתוך משימה, `task.tracks`). מסלול המכרז שייך ל-(א) בלבד. אין להתבלבל.

## 4. מודל נתונים

הגיליון מסוג `tender` מחזיק את הרשת בתוכו:

```js
{
  id, name, type: 'tender', track: 'tender',
  buildings:   [{ id, name }],                 // מבנים. ברירת מחדל: מבנה יחיד
  consultants: [{ id, name, disciplineId? }],  // יועצים. מאותחל מ-data.disciplines
  docTypes:    [{ id, name }],                 // ברירת מחדל: תכניות / מפרט / כתב כמויות
  cells: {                                     // מפתח: `${buildingId}|${consultantId}|${docTypeId}`
    "<key>": {
      events: [ { id, status, date, assignee?, note? } ],  // אותו מודל אירועים כמו היום
      statusOverride?: 'N'|'I'|'R'|'C',        // דריסה ידנית (אופציונלי)
      na?: true                                // "לא רלוונטי" — מוחרג מספירות
    }
  },
  pivot: { rows: 'consultants'|'buildings'|'docTypes',
           cols: 'docTypes'|'consultants'|'buildings' },   // ברירת מחדל למבנה יחיד: rows=consultants, cols=docTypes
  filters?: { consultantIds?, buildingIds?, statuses? }
}
```

**החלטות מפתח:**
- **רשימת יועצים** מאותחלת מ-`data.disciplines` (התחומים החיים, ניתנים לעריכה), וניתנת
  לעריכה/הוספה/הסרה בתוך הגיליון. (קיים גם `data.consultants` בשורש — לבדוק בשלב היישום
  אם ראוי לאחד מולו או להשאיר consultants בתוך הגיליון; ברירת המחדל: בתוך הגיליון.)
- **גריד מלא**: כל יועץ חייב את כל ה-docTypes; תא בודד ניתן לסימון `na:true` ("לא רלוונטי")
  והוא מוחרג מכל הספירות והאחוזים.
- מחיקת יועץ / מבנה / docType מנקה את התאים התלויים.

## 5. לוגיקת סטטוס (קריטי)

הסטטוס של תא נגזר מהאירוע האחרון בו (אותה שיטה כמו `getMostRecentEventStatus`), עם מיפוי
ל-4 דליי-המכרז. **חובה: המיפוי קורא נכון אירועי `update` (עדכון) — לא מתעלם מהם.**

| אירוע (EV_STATUSES) | דלי מכרז | צבע |
|---|---|---|
| (אין אירוע) / `missing` | **חסר** (N) | אדום |
| `progress`, `sent`, `response`, **`update`** | **בעבודה** (I) | צהוב/כחול |
| `comments` (יש הערות) | **תקוע** (R) | כתום |
| `approved` | **הסתיים** (C) | ירוק |

- **הבאג הידוע שאנחנו מתקנים כאן:** `getMostRecentEventStatus` הקיים משתמש ב-`statusMap`
  שאין בו `update` → הוא נופל חזרה ל-`task.statusId`. מסלול המכרז ישתמש בפונקציית-גזירה
  ייעודית (`tenderCellStatus(cell)`) שבה `update → 'I'` מפורשות.
- `statusOverride` גובר על הגזירה כשקיים.
- **לקח מ-status-duality:** כל קורא של סטטוס-תא (אריחים, מטריצה, מסננים, ספירות) חייב
  לעבור דרך אותה פונקציה אחת (`tenderCellStatus`) — לא לשכפל את הלוגיקה. מקור-אמת יחיד.
- התאריך המוצג בתא = תאריך האירוע האחרון. Badge `N×` = מספר האירועים בתא.

## 6. התצוגה (TenderMatrixView)

פריסה מבוססת-רפרנס (`planning_dashboard.html`), מותאמת ל-Project Hub:

1. **בקרת Pivot** (סרגל עליון): בורר "שורות" + בורר "עמודות" + כפתור **⇄ החלף**.
   - מבנה יחיד → ברירת מחדל שורות=יועצים, עמודות=מסמכים (רשת נקייה).
   - כמה מבנים → שורות=מבנים, עמודות=יועצים×מסמכים (תצוגת הרפרנס).
   - הממד השלישי (זה שלא נבחר לשורה/עמודה) מקונן בכותרת-העמודה כשצריך.
2. **אריחי סיכום** (תמונת מצב): חסר / בעבודה / תקוע / הסתיים / סה"כ-נדרש, עם אחוזים.
   מתעלמים מתאי `na`.
3. **מטריצה**: תא צבוע לפי `tenderCellStatus`, מציג סמל+תאריך אחרון + badge `N×`.
   תא `na` מוצג אפור עם "—".
4. **מסננים**: יועץ / סטטוס / מבנה (מצמצמים את המטריצה ואת האריחים יחד).

## 7. אינטראקציה

- **קליק על תא** → פאנל ציר-אירועים קטן (שימוש חוזר ברכיב האירועים הקיים, המקושר לתא).
  הוספת/עריכת/מחיקת אירוע מעדכנת סטטוס+תאריך אוטומטית.
- override ידני של סטטוס זמין מתוך הפאנל.
- עריכת רשימות (יועצים/מבנים/סוגי-מסמך) דרך מסך הגדרות-גיליון קטן.
- הכל עובר דרך ה-`save` המרכזי (undo/redo מכסה את השינויים כרגיל).

## 8. קצוות ובדיקות

- תא `na` מוחרג מספירות ואחוזים; אריח סה"כ = מספר תאים לא-`na`.
- רשת ריקה (0 יועצים / 0 מסמכים) → מצב-ריק עם הנחיה להוסיף.
- מבנה יחיד → ה-pivot לא מציג ממד-מבנה מיותר.
- החלפת pivot לא מאבדת נתונים (הנתונים בתאים, לא בתצוגה).
- בדיקות smoke ל-`tenderCellStatus`: כל אירוע→דלי נכון, דגש על `update→בעבודה`,
  `override` גובר, ותא ריק→חסר.

## 9. בסיס לפורט

`planning_dashboard.html` כבר מממש: consultants/docTypes/buildings, cells, בוררי
שורות/עמודות (pivot), אריחי-סיכום, מסננים, וטיימליין-אירועים בתא. מערכת האירועים
(`EV_STATUSES`) **זהה** לזו של Project Hub. הפורט מתאים את המבנה ל-`data.sheets`,
לסוג-גיליון `tender`, ולדליי-סטטוס המכרז.
